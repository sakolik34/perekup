# ПЕРЕКУП: GitHub, запуск и дальнейшая работа — инструкция с нуля

Эта инструкция относится к проекту в папке `/Users/aleksandrlymar/Desktop/PEREKUP`. Команды выполняются в Terminal. Не вводите их в строку адреса браузера или консоль Python. Значения `YOUR_USERNAME`, `YOUR_EMAIL` и `SERVER_IP` заменяйте своими; это обозначения, а не готовые реквизиты.

## 1. Что с чем связано

| Инструмент | Для чего он нужен |
| --- | --- |
| Папка PEREKUP | Ваши исходники: Python, HTML, CSS, JavaScript и конфигурация |
| Git | Локальная история версий и веток; работает без GitHub |
| GitHub | Удалённая копия кода, обсуждения изменений и Pull Request |
| GitHub Desktop | Графический интерфейс Git и публикации в GitHub |
| GitHub CLI (`gh`) | Авторизация и управление GitHub из терминала |
| Docker Desktop | Запуск приложения и PostgreSQL в контейнерах на компьютере |
| Docker Compose | Запуск нескольких контейнеров одной командой |
| PostgreSQL | Объявления, цены, расходы, оценки и история импорта |
| `.env` | Локальные настройки и ваш API-ключ; в GitHub не отправляется |
| GitHub Actions | Проверки кода на отдельном временном компьютере GitHub |
| Сервер/хостинг | Компьютер, на котором приложение работает, когда ваш Mac выключен |

**Размещение кода в GitHub не делает приложение работающим сайтом.** GitHub также не является резервной копией PostgreSQL или `.env`.

Рекомендуемый порядок: проверить Mock локально → сохранить код в приватном GitHub-репозитории → дождаться проверок → подключить AUTO.RIA локально → при необходимости переносить приложение на сервер.

## 2. Сначала убедитесь, что проект работает

Установите [Docker Desktop для Mac](https://docs.docker.com/desktop/setup/install/mac-install/), выбрав архитектуру вашего Mac. Перенесите приложение в Applications, запустите и завершите начальную настройку. Дождитесь готовности движка.

В Terminal:

```bash
cd /Users/aleksandrlymar/Desktop/PEREKUP
docker --version
docker compose version
docker info
```

Нужен Compose 2.24 или новее. Если ранее запущен локальный Uvicorn на порту 8000, сначала остановите его через Ctrl+C в том терминале, где он работает. При занятом порте посмотреть процесс можно так:

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

Не завершайте неизвестный процесс. В другом случае можно временно изменить в `compose.yaml` только опубликованный порт на `127.0.0.1:8001:8000` и открыть `http://localhost:8001`.

Запуск:

```bash
docker compose up --build
```

Откройте `http://localhost:8000`. В Mock-режиме автоматически появится 41 учебное объявление. Docker по умолчанию не требует `.env` или API-ключа. PostgreSQL сохраняет данные в отдельном томе.

Во втором терминале, из той же папки:

```bash
docker compose exec app pytest -q
docker compose exec app python -m scripts.seed --with-history
```

Вторая команда показывает изменения тестовых цен. Откройте дешёвый автомобиль и проверьте историю и калькулятор. API-документация доступна по `http://localhost:8000/docs`.

## 4. Путь A: GitHub Desktop — с минимумом команд

1. Скачайте [GitHub Desktop](https://desktop.github.com/) и войдите в свой аккаунт.
2. Проверьте в Terminal, является ли текущая папка репозиторием:

```bash
cd /Users/aleksandrlymar/Desktop/PEREKUP
git status
```

Если ответ `not a git repository`, выполните:

```bash
git init -b main
```

Если `git status` уже работает, повторная инициализация не нужна.

3. В GitHub Desktop выберите **File → Add local repository** и укажите существующую папку `PEREKUP`. Не создавайте вложенную папку `PEREKUP/PEREKUP`.
4. Во вкладке Changes проверьте файлы. Должны присутствовать `app`, `tests`, `alembic`, `docs`, `.github/workflows/checks.yml`, `.env.example`, Dockerfile и Compose.
5. **Не должно быть** `.env`, `.venv`, `dev.db`, логов или файлов с реальными ключами. `.gitignore` уже подготовлен. Файл `.env.example` публиковать можно: это шаблон с пустым ключом.
6. В Summary напишите `Initial PEREKUP MVP` и нажмите **Commit to main**. Commit сохраняет версию пока только на вашем компьютере.
7. Нажмите **Publish repository**, задайте имя `perekup`, оставьте **Keep this code private** включённым. Private означает, что код видите вы и приглашённые участники.
8. Нажмите Publish repository и откройте **Repository → View on GitHub**. Проверьте, что видны README и исходники.
9. Откройте вкладку **Actions**. Если запуск ожидает вашего разрешения или Actions отключены настройками репозитория, включите их в интерфейсе GitHub. Посмотрите результат workflow «Проверка приложения».

[Официальная инструкция GitHub Desktop](https://docs.github.com/en/desktop/adding-and-cloning-repositories/adding-an-existing-project-to-github-using-github-desktop).

## 5. Путь B: терминал и GitHub CLI

### 5.1. Установить и авторизовать GitHub CLI

Инструкции установки находятся на [cli.github.com](https://cli.github.com/). Если Homebrew у вас уже установлен, можно выполнить:

```bash
brew install gh
```

Если команды `brew` нет, установите CLI по официальной инструкции или используйте Desktop; не копируйте случайные команды установки из неизвестных источников.

Авторизация:

```bash
gh auth login
```

Выберите `GitHub.com`, протокол `HTTPS`, авторизацию через браузер. Подтвердите доступ своему аккаунту и настройку Git. Обычный пароль аккаунта GitHub для HTTPS Git-операций не используется. Не вставляйте токен в URL репозитория или команды проекта.

```bash
gh auth setup-git
gh auth status
```

Последняя команда показывает, какой аккаунт подключён. Это особенно полезно, если у вас несколько аккаунтов.

### 5.2. Подготовить локальную историю

```bash
cd /Users/aleksandrlymar/Desktop/PEREKUP
git status
```

Только если папка ещё не является репозиторием:

```bash
git init -b main
```

Укажите авторство **для этого проекта**:

```bash
git config user.name "Ваше имя"
git config user.email "YOUR_EMAIL"
```

Email можно взять из GitHub → Settings → Emails, включая предложенный GitHub адрес `noreply`, если не хотите указывать личный email в коммитах.

Проверьте исключения:

```bash
git check-ignore .env .venv dev.db
git status --short
```

Первое добавление файлов:

```bash
git add .
git diff --cached --stat
git diff --cached --name-only
```

Посмотрите список. Наличие `.env.example` нормально; наличие настоящего `.env` или базы — нет. Если секретный файл случайно подготовлен к первому коммиту, уберите его из индекса командой `git rm --cached -- .env` (сам локальный файл сохранится), проверьте `.gitignore` и повторите проверку. Если секрет уже опубликован, сначала отзовите/замените его: простое удаление из последнего коммита не удаляет историю.

```bash
git commit -m "Initial PEREKUP MVP"
```

### 5.3. Создать приватный репозиторий и отправить код

Эта команда действительно создаёт удалённый репозиторий и загружает ваш код:

```bash
gh repo create perekup --private --source=. --remote=origin --push
```

Если репозиторий с таким именем уже существует, **не повторяйте создание**. Используйте следующий раздел про существующий репозиторий или выберите свободное имя.

Проверка результата:

```bash
git remote -v
git status
gh repo view --web
```

`origin` — условное имя удалённого адреса. `main` — основная ветка. `push` отправляет коммиты с компьютера в GitHub.

### 5.4. Если репозиторий уже создан на сайте

Если создаёте новый пустой репозиторий через GitHub, не добавляйте через сайт README, `.gitignore` и лицензию: эти файлы/история у локального проекта свои. Для существующего пустого репозитория после локального commit:

```bash
git remote add origin https://github.com/YOUR_USERNAME/perekup.git
git push -u origin main
```

Если `origin` уже настроен, сначала `git remote -v`. Менять URL нужно только при ошибочном адресе:

```bash
git remote set-url origin https://github.com/YOUR_USERNAME/perekup.git
```

Если удалённый репозиторий **не пустой**, не используйте `push --force` и не перезаписывайте чужую историю. Для новичка проще клонировать его в другую папку, перенести туда файлы проекта без `.git`, `.env`, `.venv` и базы, посмотреть diff и создать обычный коммит.

[Официальная инструкция импорта существующего проекта](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github), [авторизация GitHub CLI](https://cli.github.com/manual/gh_auth_login).

## 6. Что делает GitHub Actions

Файл `.github/workflows/checks.yml` уже добавлен. После push или Pull Request он:

1. Загружает исходники в временное Ubuntu-окружение.
2. Устанавливает Python 3.12 и зависимости.
3. Поднимает временный PostgreSQL 16, применяет миграции и проверяет соответствие схемы моделям.
4. Выполняет тесты на SQLite и отдельно на PostgreSQL в изолированных тестовых схемах.
5. Проверяет синтаксис JavaScript.
6. Собирает Docker-образ, запускает Compose и запрашивает `/health`.
7. Останавливает тестовые контейнеры. При ошибке сохраняет журналы в выводе workflow.

**API-ключ AUTO.RIA для этого не нужен.** В тестах ответы API подменены; настоящие запросы к площадке не выполняются. Тестовые данные и контейнеры не заменяют вашу рабочую базу.

Откройте GitHub → ваш репозиторий → Actions → последний запуск. Зелёная отметка означает успех; красная — откройте конкретный упавший шаг и прочитайте сообщение. Подготовленный workflow ещё не означает, что он уже успешно выполнялся: это проверится после публикации в вашем аккаунте.

Workflow запускается также вручную через Actions → «Проверка приложения» → Run workflow. Actions расходует ресурсы вашего аккаунта согласно его условиям; платные настройки специально не включались.

[Документация GitHub о PostgreSQL в Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

## 7. Как работать над изменениями

Перед работой убедитесь, что текущие изменения сохранены:

```bash
git status
git switch main
git pull --ff-only
```

`pull --ff-only` забирает обновления, но отказывается автоматически создавать merge, если истории разошлись. Если Git сообщает о несохранённых изменениях или расхождении, остановитесь и разберитесь с ними, не применяя `reset --hard`.

Создайте ветку для конкретного изменения:

```bash
git switch -c improve-filters
```

После редактирования:

```bash
docker compose up --build -d
docker compose exec app pytest -q
git diff
```

Добавляйте именно изменённые файлы, например:

```bash
git add app/static/app.js app/templates/index.html
git diff --cached
git commit -m "Improve listing filters"
git push -u origin improve-filters
```

На GitHub появится предложение **Compare & pull request**. Опишите, что изменилось и как проверено, дождитесь Actions и объедините Pull Request кнопкой Merge. Затем локально:

```bash
git switch main
git pull --ff-only
```

Ветки не нужны для каждой опечатки, но полезны для функций и экспериментов. Коммиты лучше делать небольшими и осмысленными: один законченный шаг вместо «всё сразу».

## 8. Перенос на другой компьютер

На новом компьютере установите Git, Docker Desktop и авторизуйтесь в GitHub, если репозиторий приватный.

```bash
git clone https://github.com/YOUR_USERNAME/perekup.git
cd perekup
docker compose up --build
```

В Mock-режиме этого достаточно. Для реальных данных отдельно создайте `.env` из `.env.example` и заполните ключ:

```bash
cp .env.example .env
```

В новый репозиторий `.env` не копируется автоматически — это ожидаемо. Импортированная PostgreSQL-база тоже не переносится через Git. На новом компьютере будет новая база, пока вы не восстановите резервную копию.

## 9. Подключение настоящих объявлений

1. Получите ключ на [developers.ria.com](https://developers.ria.com/).
2. Создайте `.env`, если его ещё нет. Не перезаписывайте существующий файл командой `cp` без проверки.
3. Укажите:

```dotenv
LISTING_PROVIDER=autoria
AUTORIA_API_KEY=ваш_ключ
IMPORT_INTERVAL_MINUTES=1440
AUTORIA_MAX_PAGES=1
AUTORIA_PAGE_SIZE=20
```

4. Отредактируйте `AUTORIA_SEARCH_PARAMS` по официальным ID и параметрам нужной выборки.
5. Выполните:

```bash
docker compose up -d --force-recreate app
docker compose logs -f app
```

Ключ хранится в `.env` только на машине, где работает приложение. В GitHub repository secrets его добавлять не нужно: существующий workflow работает без него. Если в будущем появится отдельное развёртывание из Actions, тогда секреты настраиваются отдельно под конкретный процесс.

Ошибка 401/403 — проверить ключ и разрешения; 429 — квота исчерпана, дождаться восстановления. Не уменьшайте интервал импорта, чтобы «пробить» ограничение. Подробности реализации и официальные ссылки: [AUTORIA.md](AUTORIA.md).

## 10. GitHub — не публичный хостинг для этого приложения

[GitHub Pages публикует статические страницы](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). Нашему приложению нужны Python/FastAPI, PostgreSQL и периодические фоновые задачи. Поэтому загрузить папку `app` в Pages и получить работающий сервис нельзя.

### Личное использование на своём сервере

Если у вас уже есть сервер с Docker и SSH, можно оставить сервис закрытым и открыть его только себе через туннель. Покупать сервер для проверки демо не требуется.

1. Установите Docker Engine и Compose на сервере по [официальной инструкции для вашей ОС](https://docs.docker.com/engine/install/).
2. Скопируйте или клонируйте репозиторий на сервер. Для приватного репозитория используйте отдельный SSH deploy key с правом только чтения; настройка описана в [GitHub Deploy Keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys). Не копируйте основной личный приватный ключ с Mac на сервер.
3. На сервере, в папке проекта, создайте `.env` и заполните настройки. Ограничьте доступ к файлу: `chmod 600 .env`.
4. Запустите:

```bash
docker compose up --build -d
docker compose ps
```

5. На своём Mac, в новом терминале, создайте туннель:

```bash
ssh -N -L 8001:127.0.0.1:8000 YOUR_SERVER_USER@SERVER_IP
```

6. Пока SSH-команда работает, откройте `http://localhost:8001` на Mac. Это ваш серверный экземпляр через защищённый SSH-канал. Ctrl+C закрывает туннель, но не останавливает серверный Docker.

В `compose.yaml` порт уже привязан к `127.0.0.1`, поэтому не меняйте его на `0.0.0.0`, если хотите сохранить такой закрытый режим. Настройте запуск Docker при старте ОС и перезапуск контейнеров, если переходите к постоянной эксплуатации; текущий Compose предназначен прежде всего для разработки.

### Если нужен публичный сайт с доменом

Это отдельный этап: сервер, домен и HTTPS, контроль доступа к импорту/расчётам, пароль PostgreSQL вместо локального `trust`, секреты, резервные копии и мониторинг. Не открывайте текущий интерфейс всему интернету без этих изменений: в MVP любой посетитель, получивший доступ, может запускать импорт и менять расходы. При выборе хостинга также проверьте, поддерживает ли он постоянно работающие фоновые задачи и постоянное хранилище базы.

### Обновление своего закрытого сервера

После успешных тестов и объединения изменений в main, в папке проекта на сервере:

```bash
git pull --ff-only
docker compose up --build -d
docker compose logs --tail 100 app
```

Локальный `.env` при обычном pull сохраняется, потому что Git его не отслеживает. Перед изменениями схемы базы делайте резервную копию. Команда запуска автоматически применяет миграции.

## 11. Резервная копия базы

Из папки проекта на машине с работающим Compose:

```bash
mkdir -p backups
docker compose exec -T db pg_dump -U perekup -d perekup -Fc > backups/perekup.dump
```

Файл содержит данные базы, не исходники. Папка `backups/` исключена из Git; храните копию ещё и в надёжном месте вне этой машины.

Для проверки восстановления создайте отдельную базу, не перезаписывая рабочую:

```bash
docker compose exec db createdb -U perekup perekup_restore_test
docker compose exec -T db pg_restore -U perekup -d perekup_restore_test < backups/perekup.dump
```

Если тестовая база уже существует, выберите другое имя. Сначала проверьте восстановление на отдельной базе, и только потом планируйте замену рабочей. `.env` сохраняйте отдельно безопасным способом; не прикладывайте его к публичным issue.

## 12. Частые ошибки

| Сообщение / симптом | Что проверить |
| --- | --- |
| `docker: command not found` | Docker Desktop и установка CLI, затем новый Terminal |
| `Cannot connect to the Docker daemon` | Запущен ли Docker Desktop и готов ли движок |
| `port is already allocated` | Предыдущий сервер/контейнер на 8000; посмотреть `lsof`, остановить только свой |
| `git: command not found` | Установка Git / Command Line Tools |
| `not a git repository` | Правильная папка; нужен ли первый `git init` |
| `Author identity unknown` | Локальные `git config user.name` и `user.email` |
| `remote origin already exists` | `git remote -v`; не добавлять второй origin, при ошибке изменить URL |
| `repository already exists` | Подключить уже созданный репозиторий вместо повторного `gh repo create` |
| `Repository not found` | Имя, владелец, доступ к private, текущий аккаунт `gh auth status` |
| Git просит пароль и отказывает | Использовать `gh auth login` / Desktop; обычный пароль не подходит |
| `non-fast-forward` | Удалённая ветка содержит новые коммиты; сначала разобраться, не применять force |
| `.env` виден в Changes | Проверить, не отслеживался ли раньше; `.gitignore` не удаляет историю |
| Actions красный | Открыть конкретный шаг; Docker, тесты и миграции имеют разные журналы |
| После `git push` сайт не изменился | Push обновил код в GitHub; работающий Docker нужно пересобрать на машине запуска |
| Новые фото не появились | Пересобрать приложение и выполнить импорт; старые URL хранятся в БД |
| После переключения на AUTO.RIA нет аналогов | Узкая/маленькая выборка, несовпадающие характеристики; посмотрите параметры импорта |

## 13. Минимальный рабочий цикл

```text
Изменить код → запустить тесты → проверить diff → commit → push
          → дождаться GitHub Actions → обновить запущенное приложение
```

Исходники, конфигурация CI и инструкции подготовлены локально. Удалённый репозиторий в вашем аккаунте не создан, исходники туда не отправлены, Actions на GitHub ещё не запускался. Для этих шагов используйте ваш аккаунт и один из путей выше.
